## Bug A — `Environment.CurrentManagedThreadId` not found on Mono 2.0

> Status: **root cause confirmed**, fix is ~10 lines

### Evidence

Server log spammed dozens of times during gameplay:
```
[Warning:SFHeadlessHost] [v0.3.4] BootstrapOracleMapInfoBroadcast:
  Method not found: 'System.Environment.get_CurrentManagedThreadId'.
```

That property is .NET 4.5+; SF runs on Mono 2.0.50727 (Unity 5.6.3's bundled runtime).

### Hypotheses considered

1. **Literal call to `Environment.CurrentManagedThreadId`** — ruled out, grep found no source-level reference.
2. **Compiler-generated iterator state-machine reference** — CONFIRMED. The C# 9 compiler (`<LangVersion>9.0</LangVersion>` in `sf-headless-host/SFHeadlessHost.csproj`) lowers `IEnumerable<T>` iterators with `yield return` into a state-machine class whose generated `GetEnumerator()` calls `Environment.CurrentManagedThreadId` to decide between returning `this` (single-threaded fast path) vs cloning the state machine (re-entrant case).

### Root cause

`sf-headless-host/SfMapTerrainHost.cs:856` — `EnumerateMapInfoProviders` is declared as:

```csharp
private static IEnumerable<MonoBehaviour> EnumerateMapInfoProviders(GameObject root)
{
    ...
    yield return mb;   // lines 865 and 872
}
```

Called from `BootstrapOracleMapInfoBroadcast` at `sf-headless-host/SfMapTerrainHost.cs:830`. The `foreach` triggers `GetEnumerator()` → `MissingMethodException` → outer `catch (Exception e)` at line 852 swallows it silently.

**Effect: MapInfo broadcasts never go out for scripted maps** (lava growing, factory belts, xmas props, EnableObjectsPerPlayer). The "v0.3.4 makes scripted maps work" claim is partial — the broadcasts succeed only on the FIRST call path that didn't go through this iterator. Subsequent map loads silent-fail.

### Why we missed it earlier

The codebase already has a comment warning about this **exact** pattern, at `sf-headless-host/SFHeadlessHost.cs:1766-1769`:

> "Boot is driven by Update() as a state machine because Unity 5.6's Mono runtime is missing IteratorStateMachineAttribute (emitted by the C# compiler for any method with `yield return`)."

ALKA's v0.3.4 (via Cursor) re-introduced exactly the pattern the comment warns against. Cursor doesn't know about Mono 2.0's missing methods.

**Safe pattern:** `IEnumerator` (non-generic) Unity coroutines do NOT trigger this — they're driven by Unity calling `.MoveNext()` directly. Existing coroutines (`OracleAutoConnectRoutine`, `DelayedMapTerrainInitCoroutine`, `SettlePhaseCoroutine`) are fine.

**Dangerous pattern:** `IEnumerable<T>` iterators with `yield return`. Only those emit `CurrentManagedThreadId` in `GetEnumerator()`.

### Fix sketch

Replace `sf-headless-host/SfMapTerrainHost.cs` lines 825–849 — eliminate the iterator helper, inline its body as eager `List<MonoBehaviour>`:

```csharp
var providers = new List<MonoBehaviour>();
foreach (var o in root.GetComponentsInChildren(codeType, true))
    if (o is MonoBehaviour mb) providers.Add(mb);
foreach (var o in root.GetComponentsInChildren(eoppType, true))
    if (o is MonoBehaviour mb) providers.Add(mb);

foreach (var mb in providers) { /* existing send loop */ }
```

Then delete `EnumerateMapInfoProviders` (lines 856–874).

### Open questions

- Should we add a pre-commit grep or CI check for `IEnumerable<` returning methods? The lesson is going to repeat otherwise.

## Bug B — NSO snapshot count collapses from 34 → 0 mid-session

> Status: **root cause confirmed**, fix is multi-step (~15 lines)

### Evidence

Snapshot telemetry from the same session:
```
tick=10800:  players=1 nsos=34 mapSync=1 mapState=1 bytes=675  (healthy)
tick=31410+: players=1 nsos=0  mapSync=0 mapState=0 bytes=30   (collapsed)
```

Then one keyframe at tick=32400 shows `nsos=26 keyframe=True` (correctly counting NSOs in the new scene), then back to `nsos=0` between keyframes.

Effect: **clients see boxes vanish for 2 seconds at a time** (between keyframes). Player input on boxes never reaches the server because the relay assumes the server "knows" about the box.

### Hypotheses considered

1. **`ResetOracleStateForRoundAdvance` permanently locks out the rebuild path** — CONFIRMED, but the mechanism is more subtle than first thought.
2. **`TickNsoFallGuard` gates on `_nsoSpawnPos.Count == 0`** — partially correct (this is one symptom, not the root)

### Root cause

Five-step dict starvation:

1. `SFHeadlessHost.cs:3113-3117` — `ResetOracleStateForRoundAdvance` clears `_nsoSpawnPos`, `_nsoLastBroadcastPos`, `_nsoLastMovedAt`, `_nsoByIndexCache`, resets `_nsoCacheLastRebuildAt = -1f`.
2. `SFHeadlessHost.cs:985-1016` — `MarkSceneNsosMovedAfterSettle` is the ONLY place that mass-repopulates these dicts (writes at lines 1009, 1010, 1012).
3. `SFHeadlessHost.cs:979` — `MarkSceneNsosMovedAfterSettle` is called from `SettlePhaseCoroutine`.
4. `SFHeadlessHost.cs:908` — `SettlePhaseCoroutine` is started only by `OnAnySceneLoadedRunSettle`.
5. `SFHeadlessHost.cs:897-902` — `OnAnySceneLoadedRunSettle` early-returns when `scene.buildIndex != Instance._currentSceneIndex`. When that gate trips, the fallback path is `ForceCompleteOracleMapLoadIfNeeded` → `RunPostMapLoadServerInit` (`SfMapTerrainHost.cs:596`), which **does NOT** call `MarkSceneNsosMovedAfterSettle`.

**Why `nsos=0` between keyframes after lockout:** `CollectActiveNsoSnapshot` (`SFHeadlessHost.cs:4704-4778`) requires `dynamicMoving || positionDrifted || recentlyActive` (lines 4759-4767). Static crates have:
- no velocity (`dynamicMoving=false`)
- no drift after first-tick refill (`positionDrifted=false`)
- `recentlyActive=false` after `NsoKeepaliveSec=3f` expires (line 4701)

All three conditions fail → 0 entries.

**Why the keyframe still shows 26:** `CollectAllNsoSnapshot` (`SFHeadlessHost.cs:4502-4532`) bypasses the dicts entirely and uses `FindObjectsOfType<NetworkSyncableObject>()` directly. The 34→26 number drop confirms a new scene loaded; the active-snapshot collapse is keepalive-dict starvation, NOT a missing scene load.

**Why `TickNsoFallGuard` permanently locks out:** `SFHeadlessHost.cs:3955` returns when `_nsoSpawnPos.Count == 0`. Same gate as above.

### Fix sketch

Three complementary changes:

1. **Stop clearing keepalive dicts on round advance.** `_nsoLastBroadcastPos` and `_nsoLastMovedAt` are keyed by NSO ushort `Index`, which is reassigned per scene; stale entries for retired indices are harmless because `CollectActiveNsoSnapshot` finds live components fresh via `FindObjectsOfType` each tick.
2. **Mirror `MarkSceneNsosMovedAfterSettle` into `RunPostMapLoadServerInit`** so the populate path runs whether the settle coroutine OR the timeout/force-complete path fires.
3. **Add a 4th condition to `CollectActiveNsoSnapshot`**: include any NSO whose id isn't yet in `_nsoLastBroadcastPos` — guarantees each NSO is broadcast at least once per session lifetime.

### Open questions

- Is option (1) safe long-term, or do stale entries for retired indices eventually cause confusion? (Probably fine — they get GC'd on overwrite or are simply never read.)

## Bug D — `MapInfoSyncableBase.Awake` Harmony postfix never fires

> Status: **root cause confirmed**, fix is small or deletable

### Evidence

Every `EnsureMapSyncObjectsRegistered` log entry shows:
```
[v26.6] EnsureMapSyncObjectsRegistered: 11 in scene=Halloween10 buildIndex=99 awake-hits=0
```

`FindObjectsOfType<MapInfoSyncableBase>()` finds 11 objects but the Awake postfix on the base class never caught any of them.

### Hypotheses considered

1. **Patch installed too late (timing)** — LOW confidence. `Plugin.Awake` calls `InstallMapTerrainAuthorityPatches()` at `SFHeadlessHost.cs:144`, before any scene loads. If the patch log line appears at startup, timing is ruled out.
2. **Polymorphism — abstract base + virtual override** — VERY HIGH confidence (smoking gun).
3. **Method signature mismatch** — LOW. Only one `Awake` exists on `MapInfoSyncableBase`.
4. **Unity `SendMessage` bypass** — MEDIUM, related to #2.

### Root cause

Per the decompile at `refs/decompiled/Assembly-CSharp/`:

- `MapInfoSyncableBase.cs:23` — declared as `protected virtual void Awake()` (abstract class, line 3)
- `GhostPlatform.cs:32` — `protected override void Awake() { base.Awake(); }`
- `MoveAlongPathUsingForce.cs:34` — `protected override void Awake() { base.Awake(); }`
- `PillarHandler.cs:20` — `protected override void Awake() { base.Awake(); }`

Unity dispatches `Awake` via SendMessage to the most-derived class. In Mono 2.0 + Unity 5.6.3, HarmonyX patches on virtual methods of **abstract** `MonoBehaviour` base classes are bypassed by Unity's internal SendMessage path. Known issue, same family as the `OnGUI`/`Update`-on-abstract-base bugs documented in BepInEx issue trackers.

Even though each override calls `base.Awake()` manually, the base method's IL has been inlined into the JIT'd leaf method or stripped from the virtual dispatch path in the way Mono 2.0 handles abstract MonoBehaviours.

### Fix sketch

Two options:

1. **Patch each concrete subclass individually**:
   ```csharp
   foreach (var t in new[] {
       AccessTools.TypeByName("GhostPlatform"),
       AccessTools.TypeByName("MoveAlongPathUsingForce"),
       AccessTools.TypeByName("PillarHandler"),
   }) {
       if (t == null) continue;
       var awake = AccessTools.Method(t, "Awake");
       if (awake != null)
           harmony.Patch(awake, postfix: new HarmonyMethod(typeof(Plugin), nameof(MapInfoSyncableBaseAwakePostfix)));
   }
   ```
2. **Delete the Awake hook entirely.** The `FindObjectsOfType` fallback in `EnsureMapSyncObjectsRegistered` already works, and it's the one actually doing the work. The current Awake hook is dead code.

### Open questions

- Are there other subclasses of `MapInfoSyncableBase` we don't know about? Add a one-time enumeration log to confirm: walk every loaded assembly, find all types assignable to `MapInfoSyncableBase`, log `Awake.DeclaringType` for each.

## Bug E — `mono.dll` access violation @ EIP `0x03ec796d`

> Status: **probable root cause identified**, distinct from prior crash

This is a NEW crash signature, **different** from the PhysX `ConfigurableJoint` debug crash documented in [`../CRASH_INVESTIGATION.md`](../CRASH_INVESTIGATION.md) (EIP `0x0057ed26` in `StickFight.exe`). This one is inside Mono's runtime.

### Evidence

From `192.168.1.115:/home/miles/sf-oracle/install/2026-05-24_095956/error.log`:
```
mono.dll caused an Access Violation (0xc0000005)
  in module mono.dll at 0023:03ec796d.
Read from location e6e4c30c caused an access violation.

EAX:    0x6f0a0005  EBX:  0x0ff6ae38  ECX:  0x2abcc2f8  EDX: 0x0192f224
ESI:    0x04b8ada0  EDI:  0x7f00ae3d
EIP:    0x03ec796d  EBP:  0x0192f228

Bytes at CS:EIP: 83 3c 81 00 75 54 3b 7d 10 73 08 8b 45 08 3b 78
```

Decodes to `cmp dword ptr [ecx + eax*4], 0; jne short ...; cmp edi, [ebp+10h]; ...`. With `ecx = 0x2abcc2f8` and `eax = 0x6f0a0005` (1.8 billion), `[ecx + eax*4]` resolves to roughly `0xe6e4c30c` — unmapped memory. Classic out-of-bounds array index.

Mono image base on this run: `0x03e00000` (preferred 0x10000000, relocated due to WINHTTP.dll/Doorstop collision). Crash function RVA: `0xc77da`. Crash instruction RVA: `0xc796d`.

### Hypotheses considered

1. **PhysX joint dump** (from the prior crash) — RULED OUT. Different EIP, different module.
2. **Mono JIT pre-scan** of an IL stream — CONFIRMED (most likely).

### Root cause

The function bounded at `mono.dll RVA 0xc77da … 0xc7e21` is the IL bytecode pre-scan loop in `mono_method_to_ir.c` — specifically `get_basic_blocks()` (verified by a DWORD string literal `0x101b79fc` in the panic block decoding to `"..\\mono\\mini\\method-to-ir.c"`).

The function walks every byte of a method's IL stream, classifies each opcode via a 256-entry category table, and for branch opcodes computes the absolute target offset and indexes into `cfg->cil_offset_to_bb` (IL offset → MonoBasicBlock array).

**The crash mechanism:** The IL pointer drifted past `header->code + header->code_size` and decoded garbage bytes as a long-branch opcode. The next 4 bytes happened to decode as a branch displacement that produced `EAX = 0x6f0a0005` — billions, clearly not a valid IL position. The indexed read into `cfg->cil_offset_to_bb[0x6f0a0005]` lands in unmapped memory → AV.

**Most likely high-level trigger** (from v0.3.4 changes):

1. **`ApplyExplosiveBlastAt`** at `SFHeadlessHost.cs:4774` — `AccessTools.Method(dpType, "Collide")` followed by `methodInfo.Invoke(...)` per Collider in the explosion radius. First time `DestructiblePiece.Collide` is invoked via this path, Mono JITs both `Collide` and its Invoke thunk.
2. **Harmony-emitted transpiler stubs** for new v0.3.4 patches (`SendBroadcastPrefix`, `InitSyncedObjectsPostfix`, `InitMapDataObjectsPostfix`, `ReadyUpPostfix`, `GetRandomWeaponIndexPrefix`). Harmony 2.x has historical bugs around `ILGenerator.MaxStack` accounting that can produce dynamic methods with wrong `code_size` headers.
3. **`InvokeOracleBossMapSetup`** scanning all MonoBehaviours and reflectively invoking `Awake`/`Start`/`Init*` — wide-footprint JIT of unknown methods.

v0.3.4 has 21 reflective `methodInfo.Invoke` callsites — high JIT churn surface.

### Reproducibility

**Probable.** JIT-time crash, not run-time, so it triggers the FIRST time a specific method is reflectively invoked under v0.3.4. Deterministic per cold start, not a heisenbug. If it's a stock SF method JIT'd via new code paths (e.g., `DestructiblePiece.Collide` on first explosion), reproduces on first explosion of a session.

### Fix sketch

Two layers:

1. **Mitigation in plugin** — replace per-Collider reflective `methodInfo.Invoke` in `ApplyExplosiveBlastAt` (line 4808) with a **cached delegate**:
   ```csharp
   private static Action<object, Vector3, float, bool> _collideInvoker;
   // at plugin init:
   var method = AccessTools.Method(dpType, "Collide");
   _collideInvoker = (Action<object, Vector3, float, bool>)
       Delegate.CreateDelegate(typeof(Action<object, Vector3, float, bool>), method);
   ```
   Avoids per-invoke trampoline JIT and re-uses a single entry point. Same pattern for the other 20 hot-path `methodInfo.Invoke` sites.

2. **Pre-warm + isolate** — at plugin `Awake`, call `RuntimeHelpers.PrepareMethod()` on every Harmony-patched target and every reflectively-invoked target. JIT happens deterministically at boot (where a crash is obvious and recoverable), not mid-match (where it kills sessions).

### Long-term diagnostic

Enable Mono debug logging at the next oracle restart:
```bash
export MONO_LOG_LEVEL=debug
export MONO_LOG_MASK=jit
```
Dumps every JIT'd method name immediately before compilation → last entry before a future crash names the offending method exactly. Add ~5 lines to `deploy/start-oracle-server.sh`.

### Open questions

- Are there other crashes with this signature in older logs? Worth grep'ing for "mono.dll" or "0xc0000005" in any retained crash dumps.

## Bug F — Box physics "feels wrong" (was going to be Unity Explorer investigation)

> Status: **root cause confirmed** — turned out to be a code-level logic bug, not an unknown-field divergence

### Symptom (recap)

Boxes ghost through players, jitter visibly, sometimes don't move on one player's screen while moving on another's, occasionally vanish. Persists across rounds; not the same as Bug B's "boxes vanish between snapshots" (which is also true but separate).

### Hypotheses considered

Originally we expected an unknown-Rigidbody-field divergence (`interpolation`, `collisionDetectionMode`, `centerOfMass`, `mIsListening`, `mHasControl`, `PhysicMaterial`, etc.). Plan was to use Unity Explorer to compare each field on server vs client. **Unnecessary** — the root cause is in the two plugins themselves.

### Root cause

**Same-side-simulates-twice race + dead client→server relay**, all visible in our own plugin source.

Chain of events:

1. **Both sides think they own NSO physics.** `MultiplayerManager.IsServer` is patched to return true on BOTH server (`SFHeadlessHost.cs:240-242`) AND client (`SFClientRecon.cs:1603-1610` forces `mHasControl=true` via NSO.Start postfix).
2. **Server runs full dynamic physics** on pushable crates — `SFHeadlessHost.cs:4748` (CollectActiveNsoSnapshot Case 0 dynamicBody branch).
3. **Client's `SfNsoClientPush.DisableAllRigidBodies_PushPrefix`** (`sf-client-recon/SfNsoClientPush.cs:55-72`) sets client `isKinematic=false` for pushable crates so local players can push them.
4. **But client's `SmoothTowardTargets`** (`sf-client-recon/SFClientRecon.cs:500-501`) forcibly sets `isKinematic=true` every frame for any NSO in `_nsoTargets`.
5. **`_nsoTargets` is never cleared** — only added to at `SFClientRecon.cs:625`. The first server snapshot for a crate adds it to `_nsoTargets` permanently.
6. **Dead-on-arrival relay.** `RelayPushableCrateUpdates` at `SfNsoClientPush.cs:102` has precondition `if (rb.isKinematic) continue`. SmoothTowardTargets has flipped kinematic=true within ~33ms of session start. **The push relay never fires.**

### Net behavior

- Crate is dynamic for ~33ms after Init (PushPrefix succeeded)
- First server snapshot arrives → `_nsoTargets[id]` populated → SmoothTowardTargets forces kinematic=true → permanent
- Player push within the ~33ms window moves the crate locally for 1 frame, then client snaps to server's stale position
- The msg-26 ObjectUpdate relay never fires (precondition fails)
- Server never receives client pushes → server's NSO positions diverge from what players actually pushed
- Snapshots from server fight against player intent

### Visible symptoms (all explained)

- **Ghost through players** — kinematic body, no collision response during lerp
- **One player sees motion, other doesn't** — Player A pushed within the 33ms dynamic window, Player B's window already closed
- **Jitter** — snapshot lerp fighting brief local dynamic moments
- **Occasional vanish** — server's `Y<-30` killbox filter while client lerps elsewhere

### Fix sketch

Three options, in increasing order of correctness:

1. **Clear `_nsoTargets[id]` on local player contact** — minimal change, restores tactile push for ~200ms after contact.
2. **Exclude pushable crates from `SmoothTowardTargets` entirely** — let local physics drive them, only correct on `>threshold` divergence from server. Cleanest.
3. **Add velocity to the snapshot wire format** so client can extrapolate properly during the snapshot interval (currently only position is sent).

Option 2 is recommended — matches the "shared physics ownership" pattern most multiplayer physics games use for player-pushed objects.

### Why we missed it earlier

Two reasons:
1. The two systems (`SfNsoClientPush` relay + `SmoothTowardTargets` smoother) were written months apart with no integration test for "what happens when both are active on the same NSO."
2. The dead-relay symptom is silent — `SendPacketToServer` would have been called every 200ms if not gated by the kinematic check. There's no log "relay didn't fire because isKinematic=true."

### Open questions

- Are there other NSO types (chains, ice) that the smoother breaks similarly? Worth a quick check after the crate fix lands.
- Should the wire format add velocity for ALL NSO types, or just pushable crates? (Bandwidth concern.)
