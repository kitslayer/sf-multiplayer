# SUMMARY — 3-Second-Match-Cycle Bug Root Cause

> ⚠️ **Deprecated (2026-06-06).** Diagnoses a bug in the abandoned Go `sfdsrv` server (`StickFightDedicatedSrv/lobbies.go`, now in [`legacy/`](../legacy)); not applicable to the current headless host. Kept for historical reference.

**One clear top recommendation for the operator:**

The 3-second-match-cycle bug is caused by `SpawnPlayer` in `StickFightDedicatedSrv/lobbies.go:1514` setting `flag = 1` whenever `!IsLobby && GetPlayerCount(true) > 1`. The stock SF client's `OnPlayerSpawned` (decompile: `MultiplayerManager.cs:1592-1640`, also Sockets variant) interprets `flag=1` as **"teleport to `Vector3(0, -100, 0)` then call `HealthHandler.ForcedDie()`"**. The patched DLL (`sf-netcodev2`) does **not** patch `OnPlayerSpawned`, so it inherits this lethal interpretation verbatim. So in every multiplayer match-start the server tells every spawning player to die instantly → kill propagates to server → `CheckWinner` → `ChangeMap` → repeat. Auto-ready (3s timer) explains the cadence. The fix is a one-line condition change in `SpawnPlayer`: only set `flag=1` for genuine late-joiners (`MatchInProgress()` already true **and** the slot has been alive earlier in this match), and send `flag=0` for the first spawn of a new round. Auxiliary action: also fix the `posX==0 && posY==0 && posZ==0` guard in the same function — the patched DLL actually sends `(0, 12, 0)` (not all-zero) for non-lobby maps, so the dumped-map spawn override never triggers; loosen the condition or treat any client-asserted `(0, *, 0)` as "use dumped spawn." See `notes/recon/BUG_3SEC_MATCH_CYCLE.md` for the full evidence trail and `notes/design/FIX_FLAG_LOGIC.md` for the design.
