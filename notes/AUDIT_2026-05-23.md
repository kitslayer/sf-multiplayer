## Finding 1 — There are TWO independent sync systems for level objects, and we only handle one

**Discovered during platform-sync investigation.** Stick Fight's level/world syncing splits across two completely separate mechanisms:

| System | Stock SF class | Used by | Wire mechanism | Our handling |
|---|---|---|---|---|
| **NetworkSyncableObject** (NSO) | `NetworkSyncableObject.cs` | Boxes, ice, chains, crates, ragdoll-like physics props | `ObjectUpdate` (msgType 26, channel 10) at 5Hz + v26 `WorldStateSnapshot` (39) at 30Hz | ✅ Fully handled. Oracle is authoritative, snapshot includes position + rot. |
| **MapInfoSyncableBase** | `MapInfoSyncableBase.cs` | `GhostPlatform`, `MoveAlongPathUsingForce`, `PillarHandler`, `PlayMoveAnimations` | `MapInfoSync` (msgType 33) at 5Hz | ⚠️ Pass-through only. Our `SendBroadcastPrefix` forwards MapInfoSync packets unmodified, but we add no extra reliability or position correction. Inherits stock's fragile lookup. |

**Why this matters**:
- Boxes and ice ARE NSOs. Our v26 snapshot covers them. (They have OTHER bugs — see Finding 2.)
- Platforms (`GhostPlatform`) are NOT NSOs. They sync via the dictionary-keyed `MapInfoSync` path that's vulnerable to lookup failures (Finding 3).

**Source evidence**:
- `refs/decompiled/Assembly-CSharp/GhostPlatform.cs:4` — `public class GhostPlatform : MapInfoSyncableBase`
- `refs/decompiled/Assembly-CSharp/MapInfoSyncableBase.cs:23-34` — Awake registers via `AddMapDataObject(Vector2 pos, this)`
- `refs/decompiled/Assembly-CSharp/MultiplayerManager.cs:1147-1161` — `GetObjectToSync(Vector2)` errors silently if key not in dict

## Finding 2 — Destruction race re-introduced by the recent hybrid client-NSO patch

Commit `6875908` (phase 6.18: "60Hz default + /tickrate chat command + hybrid client NSO") re-enabled `Patch 1` (skip `DisableAllRigidBodies` so client NSOs stay dynamic for local push responsiveness) while keeping `Patch 2` removed (no `mHasControl=true` forcing, so clients don't broadcast NSO positions).

**The trap**: dynamic-but-not-broadcasting client NSOs can still fire `DestructiblePiece.OnCollisionEnter` locally. The destruction flow then routes through:

```
Client-local collision
  → DestructiblePiece.OnCollisionEnter (DestructiblePiece.cs:47)
  → Collide() with force.magnitude*mult > forceThreshold
  → SendDestructMessage(force, mult)
      → IF MultiplayerManager.IsServer: apply locally + OnDestructibleDestroyed broadcast
      → ELSE: SendP2PPacketToServer(ObjectDestructionCollision, channel=11)
```

On a client (non-host), `SendDestructMessage` sends `ObjectDestructionCollision` to the server. Our server's `RelayBodyToAll` forwards back to all clients (sender included) — so client-initiated destructions DO propagate correctly.

But on the SERVER, the oracle's same DestructiblePiece can also fire `OnCollisionEnter` from its own physics. That outbound destruction message gets caught by our filter at `SFHeadlessHost.cs:618-624` (the P0-6 fix) and dropped. Two scenarios where this matters:

1. **Spurious server destruction (filter works correctly)**: oracle's box drifts off-platform into killbox → server-local destruction fires → filter blocks → clients don't lose their intact boxes. ✓
2. **Race against a real destruction (filter masks a real event)**: oracle's box really does break first (because oracle ran 1 fixed-tick ahead) → server-side destruction fires → filter blocks → no client gets the destruction → oracle thinks box is gone but clients still have it → eternal desync. ✗

There's no signaling difference between case 1 and case 2 — the filter is a coarse drop-all.

**Severity**: low frequency but high impact (one missed real destruction = permanent box "ghost" on clients). Probably accounts for some "boxes randomly vanish on one screen and not the other" reports, especially after the box gets pushed near the killbox edge.

**Why chains don't show this**: chains use the `eventDestruction` code path (`DestructiblePiece.cs:121-148`) which is local-only and doesn't broadcast via `ObjectDestructionCollision`. They're stable because their destruction is fully client-side and visual-only.

**Source evidence**:
- `sf-headless-host/SFHeadlessHost.cs:618-624` — destruction filter
- `sf-headless-host/SFHeadlessHost.cs:1137-1152` — re-added `SkipPrefix` patch (commit `6875908`)
- `refs/decompiled/Assembly-CSharp/DestructiblePiece.cs:47-68, 98-119` — OnCollisionEnter + SendDestructMessage flow
- `refs/decompiled/Assembly-CSharp/DestructiblePiece.cs:130-148` — force-threshold + `mSentDestructionForThisPiece` guard

**Possible fixes (none implemented per audit scope)**:
- A) Drop the filter entirely; instead, mark server-originated destructions so they're not filtered, only forward them when the client's local NSO state matches (requires per-NSO state tracking on the server)
- B) Replace the filter with a Y-coordinate guard: only drop destructions where the destroyed NSO's last-known Y < -30 (killbox-only)
- C) Add a `destroyedNsoIds` list to v26 `WorldStateSnapshot` so clients can authoritatively delete their local copies from the server's view, separating sync from event broadcast
- D) Revert the hybrid client patch and accept ~RTT box-push lag (the trade in P0-5's original fix)

Option C is the architecturally cleanest; it's a v26 protocol bump (v26.4). Option B is the simplest patch.

## Finding 3a — MoveAlongPathUsingForce + PillarHandler run physics independently on every client (DRIFT GUARANTEED)

This is a bigger finding than the precision-key issue. Inspecting two of the three `MapInfoSyncableBase`-derived map objects shows a fundamental architectural choice in stock SF: **the sync packet only includes abstract state (waypoint index, accumulated value), but the actual position is integrated locally on every client**.

`MoveAlongPathUsingForce.Update` (`MoveAlongPathUsingForce.cs:61-109`):
```csharp
// Runs on EVERY client unconditionally:
rig.AddForce(vector * num * speedChangeMultiplier * Time.deltaTime * forceAmount, ForceMode.Acceleration);

// Only server progresses the target waypoint + sends SetData:
if (MatchmakingHandler.IsNetworkMatch && !MapInfoSyncableBase.m_NetworkControl) return;
if (Vector3.Distance(...) < 1f) { ... SendNewStatePackage(); }
```

`GetData` / `SetData` only sync `currentTargetId` (a byte). Position is whatever the local `Rigidbody.AddForce` integration has produced since the last waypoint change.

`PillarHandler.MoveTowardsValue` (`PillarHandler.cs:54-58`):
```csharp
velocity += (startPosition + value - base.transform.position.y) * Time.deltaTime * 20f;
base.transform.position += new Vector3(0f, velocity, 0f) * Time.deltaTime;
```

This is a spring integrator running locally on every client. `value` is sync'd, but `velocity` is local. Same drift.

**Why this guarantees drift in our setup**:
- Unity physics isn't deterministic across machines (different CPU FP behavior, FixedUpdate scheduling, frame timing).
- Each client integrates these per-frame for tens of seconds between waypoint changes.
- Clock skew of just 16ms + slightly different `Time.deltaTime` values = visible position offset within a few seconds.

**Why "GhostPlatform works but my moving platforms don't" is a real observation**: `GhostPlatform` doesn't integrate position — it snaps via `transform.localPosition = startPosition` or `startPosition + Vector3.right * 2f` (`GhostPlatform.cs:139, 161`). If `SetData` arrives, the snap is identical on every client. Drift-free.

**Severity**: high on maps with `MoveAlongPathUsingForce` or `PillarHandler`. These are SF's "moving platform" and "pressure-plate elevator" mechanics — both important for traversal-heavy maps.

**Possible fixes** (all need code, none implemented in this audit):
- A) Server-authoritative position broadcast in v26 `WorldStateSnapshot` — extend snapshot with a `MapInfoSyncable` section: `[u16 instanceCount, [u32 instanceID, f32 x, f32 y, f32 z]×n]`. Cheapest, highest impact.
- B) Kill local physics on these objects via a client-side Harmony patch — kinematic + `mNetworkManager == null` skip. Then they don't move at all locally, just snap when `SetData` arrives. Cheap but stutters at 5Hz sync rate without smoothing.
- C) Determinism patches — sync `velocity` along with `value`, force `Time.fixedDeltaTime` to be identical across machines. Brittle; doesn't address timing skew between fixed updates.

Option A is the right call. Same fix-shape as our NSO snapshot work.

## Finding 3b — GhostPlatform / MapInfoSync dictionary key precision

User-reported "platforms different on each client" maps to a known-fragile path in stock SF.

**Flow**:
1. At map load, every `MapInfoSyncableBase`-derived component runs its `Awake`:
   ```csharp
   Vector3 position = base.transform.position;  // world position
   m_StartPos = new Vector2(position.y, position.z);
   m_NetworkManager.AddMapDataObject(m_StartPos, this);
   ```
   (`MapInfoSyncableBase.cs:30-32`)
2. Server's `GhostPlatform.Update` advances the on/off timer (only `m_NetworkControl=true`, i.e., `IsServer`):
   ```csharp
   if (!MatchmakingHandler.IsNetworkMatch || MultiplayerManager.IsServer) { ... StartCoroutine(FadeOut()); }
   ```
   (`GhostPlatform.cs:70-93`)
3. Server's `MapInfoSyncableBase.SendNewStatePackage` → `MultiplayerManager.SyncMapData(this)` writes `[f32 startPos.x][f32 startPos.y][bytes data]` and `SendMessageToAllClients(MapInfoSync, ...)` on channel 0
4. Client's `OnMapDataRecieved` reads the same `Vector2` → `GetObjectToSync(objectPos)` → dictionary lookup
5. If `mMapDataObjectToSync.ContainsKey(objectPos)` is false → logs `"Could not find MapObject with pos: X Y"` and SetData never fires

**The precision concern**: `position.y` and `position.z` are world-space floats. Both server and client are running the same scene additively loaded into the same MainScene. If the scene's root transform finalizes at a different microsecond on each side (additive load → physics quiescence → ...), the platform's Awake-time `base.transform.position` can differ by a few ULPs of float32. The Vector2 dictionary uses `Equals` which is bit-exact. One ULP off = lookup fails forever for that platform.

**Why this might be the user's "different per client" report**:
- Each client's lookup fails INDEPENDENTLY. Client A's lookup might succeed, Client B's might fail.
- Failed-lookup clients have `GhostPlatform.isOn` stuck at the initial `true` (line 22).
- Successful-lookup clients receive `SetData` and toggle on/off in sync with the server.
- Net effect: platforms visible to one client are invisible to the other within ~5-10s of match start.

**Severity**: medium. Specific to maps with `GhostPlatform` / `MoveAlongPathUsingForce` / `PillarHandler`. Empirically this is a small minority of the 123 Landfall maps (chains/boxes are far more common). But on those specific maps, the experience is significantly broken.

**Source evidence**:
- `refs/decompiled/Assembly-CSharp/MapInfoSyncableBase.cs:30-32` — key construction
- `refs/decompiled/Assembly-CSharp/MultiplayerManager.cs:1147-1161` — silent lookup-failure
- `refs/decompiled/Assembly-CSharp/GhostPlatform.cs:79` — `!IsNetworkMatch || IsServer` gates the state machine
- `refs/decompiled/Assembly-CSharp/GhostPlatform.cs:164-187` — SetData applies the server's state with `StartCoroutine(FadeIn/FadeOut)` only on receipt

**Possible fixes**:
- A) Diagnostic logging on the oracle: log `Vector2 m_StartPos` for every `AddMapDataObject` call + Vector2 from every `SyncMapData` outbound. Compare to a client's `OnMapDataRecieved` Vector2 reads to confirm the ULP mismatch hypothesis.
- B) Add a server-side patch that rounds `m_StartPos.x` and `m_StartPos.y` to 3 decimals before adding to the dict, AND rounds the wire-emitted Vector2 to the same precision. Symmetric rounding on the client side via another Harmony patch.
- C) Replace the Vector2 key entirely with `GetInstanceID()` of the GameObject. Bigger change — would require patching every site that reads/writes the dict.
- D) Build a server-authoritative platform path: have the oracle broadcast every `GhostPlatform.isOn` state at 30Hz in v26 `WorldStateSnapshot` (new section), with platform identity by `transform.GetInstanceID()` or `transform.name`+sceneIndex. Bypasses the brittle key entirely. v26.5 protocol bump.

Option D is right for the long term. Option B is the cheapest stop-gap.

## Finding 3c — Ice randomly breaking — same family as boxes, plus reconciliation-collision hypothesis

"Ice" in SF is not a separate class — every ice block is a `DestructiblePiece` riding on a `NetworkSyncableObject`, distinguished only by an `IceDestructionAudio` component reference (`DestructiblePiece.cs:24`). The destruction flow is identical to boxes:

```
DestructiblePiece.OnCollisionEnter
  → Collide(collision.relativeVelocity * 0.1f, multiplier)
  → if (force.magnitude * mult > forceThreshold) SendDestructMessage(force, mult)
```

So "ice randomly breaks" is the same root-cause family as P0-11. **Additional hypothesis specific to ice/destructible-on-reconciliation**:

With dynamic client NSOs (commit `6875908`), every client now runs its own ice/box physics for the duration between snapshots. When a snapshot arrives, `SFClientRecon` lerps the local NSO transform toward the server's reported position. If the lerp delta is large (e.g., a fast-moving box near an ice block), the swept motion of the box during lerp interpolation can produce a collision event with the ice that doesn't exist on the server (because on the server, the box reached its position via continuous force application, not a teleport).

```
Server: box force-applied → contiguous trajectory → no surprise ice collision
Client: snapshot arrives → box lerped over 33ms toward target → swept motion intersects ice → OnCollisionEnter fires → relativeVelocity is HIGH because lerp covers ~2 units in 33ms → force.magnitude crosses threshold → ice broadcasts destruction → propagates everywhere
```

The destruction filter doesn't catch this because it's a CLIENT-initiated event passing through `RelayBodyToAll`, not a server-originated one.

**Severity**: low-to-medium frequency, but visually striking (random ice shatter unrelated to player action). Less common when network conditions are good (snapshot deltas are small, lerp gentle).

**Possible mitigations**:
- A) Set the local NSO's `Rigidbody.isKinematic = true` *only during snapshot apply* and restore to dynamic after. Kinematic bodies don't generate `OnCollisionEnter` events with other dynamics from MovePosition sweeps (in Unity's default settings). The interpolated motion no longer fires destruction collisions.
- B) Increase `forceThreshold` on ice when in network match. Requires per-piece tuning.
- C) Disable client-side destruction during reconciliation entirely — only let client-initiated destructions through if they're driven by a local player collision (check `collision.rigidbody.transform.root` for the local Controller, similar to the existing `HasControl` guard at `DestructiblePiece.cs:62`).

Option C is the cleanest: tighten the existing `HasControl` guard so non-player-driven local collisions never trigger destructions.

## Finding 4 — Channel routing is correct (false-alarm flags audited)

The channel-routing audit flagged two msgTypes (`PktWeaponWasPickedUp` on channel 1, `PktWorkshopMapsLoaded` on channel 1) as potential mismatches. Cross-checking against `refs/decompiled/Assembly-CSharp/P2PPackageHandler.cs:310-344` (`GetChannelForMsgType` — the ground truth):

```csharp
MsgType.WeaponWasPickedUp     => 1,    // we use 1 — MATCH
MsgType.WorkshopMapsLoaded    => 1,    // we use 1 — MATCH
```

**Conclusion**: zero channel-routing bugs in the current code. The specific-channel msgTypes (PlayerUpdate on `slot*2+2`, ObjectUpdate on 10, etc.) are all correctly preserved through the relay path.

This matches the existing closed-without-code-change note **C-3** in `BUGS_BACKLOG.md`. The false-flag has now been cross-verified.

## Finding 5 — Box position drift root cause is server-side authoritative state, not client divergence

Original assumption: clients had divergent box positions because each client was simulating boxes locally. That was true under the old client-shim regime (commit `6b1a9e4` removed it).

Current state: each client gets server-authoritative box positions via v26 snapshot at 30Hz. With the commit `6875908` hybrid patch (dynamic NSOs locally, but `mHasControl=false`), local push works fluidly and snapshot reconciliation lerps toward the server's view.

**What could still cause cross-client position differences**:
- Snapshot is filtered to "non-static NSOs" using a position-delta threshold (`CollectActiveNsoSnapshot` includes NSOs whose position changed since last broadcast, with 1s keepalive after motion stops, plus Y > -30 filter). If a box stops moving, it falls out of the snapshot stream. If a NEW client joins after that, they won't get the box's position in any snapshot until something pushes it again. → **First-snapshot-after-join gap**.
- The Y > -30 filter is correct for boxes that fall off the killbox but ALSO drops legitimately-low NSOs on maps with low play zones.
- The v26 snapshot does NOT include rotation around X or Y, only Z (`f32 rotZ`). Boxes that rotate around X/Y can visually differ between clients. Probably minor for SF since most pushes only rotate around Z, but worth noting.

**Severity**: low. Mostly visible right after a client joins; usually resolves once the next push happens.

**Source evidence**:
- `sf-headless-host/SFHeadlessHost.cs:3186` — `BroadcastWorldStateSnapshot`
- `sf-headless-host/SFHeadlessHost.cs` — `CollectActiveNsoSnapshot` (greppable nearby)

**Possible fix**: send a full-NSO keyframe snapshot on first `PktPlayerInput` from each new client's endpoint, regardless of position-delta. Cheap, fixes the join gap.

## Finding 6 — `NetworkSyncableObject.mHasControl` is `static` (one global value, not per-NSO)

While auditing the destruction-race path I noticed `NetworkSyncableObject.cs:42`:

```csharp
private static bool mHasControl;
```

It's a STATIC field. Every NSO in the process shares the same value. `Start()` sets it to `MultiplayerManager.IsServer` (line 192), and `UpdateHost()` re-sets the same (line 208).

Implications:
- Stock SF expects `IsServer` to be consistent across the process. The host has it true; clients have it false. So the static-ness is fine in stock.
- Our previous client-side shim that set `mHasControl=true` on individual NSO instances actually mutated the GLOBAL static — so it affected EVERY NSO at once, which is why the old "client-shim cross-fire" was so destructive (every client's every NSO claimed authority).
- The current build (commit `6875908`) removed that direct write. Clients have `mHasControl=false` (set by the most recent `Start()`).

This explains why the cross-client NSO fight in P0-5 was so total — it wasn't N=4 boxes drifting, it was every single NSO in the scene having mHasControl=true simultaneously.

## Finding 7 — `DisableAllRigidBodies` has implicit exemptions we need to respect

`NetworkSyncableObject.DisableAllRigidBodies` at line 222-235:

```csharp
private void DisableAllRigidBodies()
{
    if (Application.isPlaying)
    {
        bool flag = base.gameObject.GetComponent<MoveAlongPathUsingForce>() != null;
        Rigidbody[] componentsInChildren = GetComponentsInChildren<Rigidbody>();
        int num = componentsInChildren.Length;
        for (ushort num2 = 0; num2 < num; num2++)
        {
            componentsInChildren[num2].isKinematic = !flag && !m_HardSync;
        }
        mIsListening = true;
    }
}
```

Stock SF's "kinematic on non-host" behavior has TWO automatic exemptions:
- `MoveAlongPathUsingForce` components stay dynamic (they need their `AddForce` integration in local Update)
- NSOs marked `m_HardSync` stay dynamic

Our `SkipPrefix` patch (commit `6875908`) skips the entire function — which means we ALSO skip the exemption logic. That's fine because we want everything dynamic, but the symmetry tells us: stock SF already acknowledges that some NSO types can't survive kinematic-on-client. The fact that those exemptions exist is a hint that `MoveAlongPathUsingForce`'s drift problem (Finding 3a) is a known compromise even in stock SF (because making it kinematic would freeze its motion entirely; stock SF chose drift over freeze).

Our Phase 6.18 server-authoritative platform fix should make these objects kinematic on clients AND drive their position from the v26 snapshot. That gets the best of both worlds — no local drift, no frozen platforms.

## Finding 8 — Attacker-slot spoofing bypasses damage distance check (low-severity anticheat gap)

A separate audit pass on the damage + weapon + anticheat code found one real gap.

`ValidateDamagePacket` (`SFHeadlessHost.cs:2009-2078`) validates the body's attacker-index byte for range (must be 0-3 or 255-for-environment), then performs a distance check by looking up the attacker's recent position via the rewind buffer. The lookup uses the body's attacker byte as the slot key, not the sender's authenticated slot.

A malicious client can spoof a different attacker slot in their damage packet:
- Real sender: slot 1 (authenticated at `ClientRequestingIndex` time)
- Body claims: `attackerIdx = 3` (slot 3, perhaps standing on the far side of the map near the victim)
- Distance check loads slot 3's position, not the sender's. If slot 3 is closer to the victim, the spoofed packet passes the 50u range check.

The rate-guards still apply per-IP so this isn't an unlimited-damage exploit, but it does let a malicious client deal damage at impossible-from-their-position ranges as long as ANY other player is plausibly close enough.

**Severity**: low. Requires the attacker to know other players' positions (which the snapshot stream gives them) and craft believable distance claims. The 50u cap still bounds the maximum range broadly.

**Fix**: trivial. At the top of `ValidateDamagePacket`, add:
```csharp
if (attackerIdx != 255 && attackerIdx != sender.Slot) return false;
```

Caught attackers can't pretend to be someone else. Filed as **P1-8** in BUGS_BACKLOG.md.
