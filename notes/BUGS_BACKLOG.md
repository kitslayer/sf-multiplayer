# Bug backlog — incident log

Every non-trivial bug we've hit, ordered by impact, with the root cause and the commit that fixed it. Format mirrors ALKA's `BUGS_BACKLOG.md` (P0/P1/P2 priority bands).

> See [`OBJECT_SYNC.md`](OBJECT_SYNC.md) for the architectural reference on how SF's three world-state sync mechanisms (NSO, MapInfoSyncableBase, DestructiblePiece events) interact — most P0 bugs in this file are at the boundaries between those systems. The [`AUDIT_2026-05-23.md`](AUDIT_2026-05-23.md) doc has the full evidence trail for the currently-open bugs (P0-11 through P0-15).

## P0 — Critical / blocking

| ID | Bug | Root cause | Fix | Commit |
|----|-----|-----------|-----|--------|
| P0-1 | **Players see each other frozen after a 2nd client joins.** Symmetric: both clients see the other not moving. | `HandlePlayerUpdate` forwarded `PktPlayerUpdate` on channel **0** (hardcoded), but `NetworkPlayer.InitNetworkSpawnID` sets `mUpdateChannel = slot*2 + 2` and the receiver's NetworkPlayer only listens on that specific channel. Channel-0 forwards were silently dropped at the dispatch layer. | Preserve the incoming channel through `SfDispatch` → `HandlePlayerUpdate` → forward on same channel. | `85b4125` |
| P0-2 | **Both clients' SfClient records had each other's SteamIDs after a 2nd join.** Detected via `[SF DEBUG]` log: slot 0's record changed from real Steam ID to Goldberg fake ID right when slot 1 joined. | `SfDispatch` had `if (steamID != 0) cli.SteamID = steamID` per packet, but SF's `P2PPackageHandler.SendP2PPacketToUser` puts the **destination's** SteamID in the envelope, not the sender's. When the new `PktClientJoined` triggered `OnClientJoined.PingAllUsers()` on P1, P1 sent a Ping with envelope.steamID = P2's. Our server overwrote P1's SfClient with P2's SteamID → routing broken. | Only set `cli.SteamID` once from `ClientRequestingIndex` body (which DOES carry sender identity). Per-packet envelope is unreliable. | `b4c3d3f` |
| P0-3 | **PktClientSpawned arrives before PktClientJoined**, causing existing clients to NullRef in `OnPlayerSpawned` (which reads `mConnectedClients[b].ControlledLocally`). | Initial `PktClientJoined` implementation called `BroadcastSfPacket(PktClientSpawned)` first, `PktClientJoined` to peers second. Existing client received Spawned with empty `mConnectedClients[slot]`. | Reorder: send `PktClientJoined` to existing peers FIRST, then `BroadcastSfPacket(PktClientSpawned)`. | `45330fb` |
| P0-4 | **`HandlePlayerUpdate` stops forwarding the moment `/start` is typed.** Movement syncs in lobby, freezes in match. Heartbeat showed `clients=2 spawned=0 rx=97/s` after match start. | `BroadcastStartMatch` resets every `cli.Spawned = false` (intended to signal "needs fresh respawn for the round"). `HandlePlayerUpdate` was gating `if (!Spawned) continue;` which skipped ALL clients post-start. | Gate on `cli.Initialized` (set once after `ClientInit`, never reset) instead. | `91ae4dc` |
| P0-5 | **Boxes desync between clients — different positions on every screen — and random vanish events.** | Client-side shim (`InstallClientModePatches`) was setting `NetworkSyncableObject.mHasControl = true` + skipping `DisableAllRigidBodies` on every connected client. With 2+ clients connected, ALL claimed authority over every NSO — each broadcasting their own physics result + running local destruction-collision logic. Boxes diverged; spurious local destructions on one client propagated to others via the relay path → boxes randomly vanished. | Initially: removed both client-side NSO patches (commit `6b1a9e4`) → cross-client fight gone, but box-push felt laggy (~RTT). Then re-added `Patch 1` (dynamic NSOs) WITHOUT `Patch 2` (no `mHasControl=true`) — see [AUDIT_2026-05-23.md](AUDIT_2026-05-23.md) Finding 2. Hybrid state today: clients have dynamic NSOs (instant push feedback) but don't broadcast, so the oracle remains sole authority. Trade-off: introduces P0-11 (destruction race against the server-originated filter). | `6b1a9e4` → `6875908` |
| P0-6 | **Ice / chains break "for no reason" not near any player.** | Oracle's own host-side code generated spurious `ObjectSimpleDestruction` / `ObjectInvokeDestructionEvent` / `ObjectDestructionCollision` events for its scene's NSOs (chains stress-breaking under joint forces on map load, boxes that drift off platforms hitting the killbox). Our `SendBroadcastPrefix` forwarded them to clients, who removed intact local objects. | Skip outbound forwarding of msgTypes 28/29/30 in `SendBroadcastPrefix`. Client-initiated destructions still propagate via the inbound `RelayBodyToAll` path (P0-7's fix kept intact). | `f44cd6a` |
| P0-7 | **Ice / crate breaks visible only to the player who broke them.** Other clients saw the destructible intact. | `PktObjectSimpleDestruction` (28) / `PktObjectDestructionCollision` (30) were going through `RelayBodyToOthers` (excludes sender). In vanilla SF the *host* applies the break locally and broadcasts to non-host clients; in our dedicated-server setup NO client is the host — the sender hasn't applied locally either and needs the echo back. Same fix shape as the `PlayerTookDamage` killing-blow signal. | Switch destruction events to `RelayBodyToAll` (sender included). Also added msgType 29 to the handler (was unhandled-default). Lifted from ALKA's `BUGS_BACKLOG.md` P0-3. | `7dd1302` |
| P0-8 | **Server-side boxes vanish at Y=-50 broadcast to clients.** | Server-side NSOs were broadcasting positions to clients via the v26 `WorldStateSnapshot`. When server NSOs fell off the killbox into oblivion (Y≈-50), the snapshot included those positions → clients applied → local copies vanished off-screen. The v25 `ObjectUpdate` forwarding had a Y < -30 filter already; the v26 snapshot didn't. | Add the same Y < -30 filter to `CollectActiveNsoSnapshot`. | `64acd24` |
| P0-9 | **`stop-lobby.sh` killed user's running game windows.** | The sweep `pkill -f "StickFight.exe.*-port ${PORT}"` matched ALL SF processes connected with `-port 1337`, including Steam SF and the 2nd local player. | Replace with a lobby-specific match against the oracle's `-logFile sf-oracle-unity-${BRIDGE}.log`, which only appears on the oracle's command line. | `3f5f100` |
| P0-10 | **Map-preset weapons don't spawn on clients.** "I cant grab guns that spawn on some maps and theres maps where guns only spawn in certain spots." | `WeaponPickUp` prefabs in level geometry register via `InitWeaponPickUpOnAwake` → `MultiplayerManager.AddPreSpawnedWeapon`. Stock SF broadcasts via `CheckForGroundWeapons` (msgType 31) from `GameManager.StartMapSequence` after `IsNetworkMatch=true`. On our oracle that coroutine doesn't reach the network branch on scene load. | Add `CheckForGroundWeapons` invocation to `InvokeMultiplayerManagerInitChain` (manual init chain). | `8567cf7` |
| P0-11 | **Destruction race re-introduced by hybrid dynamic-NSO client patch.** With clients running dynamic NSOs (commit `6875908` re-added `Patch 1`, kept `Patch 2` off), the server-originated destruction filter at `SFHeadlessHost.cs:618-624` was too coarse: dropped ALL outbound destructions to prevent killbox-fall destructions, but also dropped legitimate server-side breaks. Oracle thinks box gone, client still has it → "ghost box". | Replaced the unconditional `msgType==28||29||30 → skip` with a Y-aware check. New `NsoIsKillboxFallen(idx)` helper looks up the NSO position by index; only skips if `position.y < -30` (the killbox-fall case). Legitimate destructions above the killbox now forward to clients. | `c6e9797` |
| P0-12 | **`GhostPlatform` and other `MapInfoSyncableBase` map objects desync via the Vector2-key dictionary lookup.** `MapInfoSyncableBase.Awake` keys the dictionary by `new Vector2(position.y, position.z)` with bit-exact float `Equals`. Server and clients can disagree by a few float32 ULPs from physics quiescence at additive-load timing. Failed lookup silently drops `SetData` → clients stuck in initial state for affected platforms. | Two Harmony prefixes on `MultiplayerManager.AddMapDataObject` + `OnMapDataRecieved` that quantize the Vector2 to 0.01 precision. AddMapDataObject prefix also writes the quantized value back into `MapInfoSyncableBase.m_StartPos` so the outbound `SyncMapData` wire emits the quantized key. Installed on both server and client (same DLL, both branches). | `c6e9797` |
| P0-13 | **First-snapshot gap for late-joining clients on NSOs at rest.** `CollectActiveNsoSnapshot` only includes NSOs whose position changed since last broadcast. After a box stops moving, it falls out of the snapshot stream. Late-joining clients see prefab spawn positions until something pushes them again. | When `HandlePlayerInput` registers a new v26 endpoint for a slot, call `SendKeyframeSnapshotToEndpoint(from)`. New `CollectAllNsoSnapshot` skips the position-delta filter (Y > -30 still applies). One-shot full snapshot to each new endpoint; regular delta stream resumes after. | `c6e9797` |
| P0-14 | **`MoveAlongPathUsingForce` and `PillarHandler` drift across clients because every client integrates physics locally; only abstract waypoint/value state is sync'd.** Likely the dominant cause of "platforms look different on each client". | v26.5 wire-format bump. New `mapSync` section in `WorldStateSnapshot` carries `[f32 startX, f32 startY, f32 x, f32 y, f32 z]` per `MapInfoSyncableBase` instance — keyed by the same `m_StartPos` Vector2 that stock SF's MapInfoSync uses (quantized by P0-12 so server + client agree bit-exactly). On first sight, client forces the object's Rigidbody kinematic so local AddForce / spring integrator stops fighting the snapshot stream. Smoothing loop lerps toward server target each frame. | `7b5a037` |
| P0-15 | **Ice randomly breaks during snapshot-lerp reconciliation.** With dynamic client NSOs, the swept motion of a local NSO being lerped toward a server-reported position can fire `OnCollisionEnter` on adjacent destructibles with high `relativeVelocity` → `SendDestructMessage` → server forwards → ice "randomly" shatters for everyone. | Harmony prefix on `DestructiblePiece.OnCollisionEnter` in SFClientRecon returns false (skip stock) if the colliding rigidbody's root was lerped in the last 150ms. `_recentLerpAt` is now written in `ApplyNsoSnapshot` only when the snapshot delivers a LARGE position delta (>0.3u) — the actual teleport-into-ice case. Normal active-push deltas (~0.05-0.1u per snapshot) don't trigger the suppression, so legitimate kicks still register destructions. | `c6e9797` + `7b5a037` (tightening) |

## P1 — Significant / fixed

| ID | Bug | Root cause | Fix | Commit |
|----|-----|-----------|-----|--------|
| P1-1 | **Boxes don't move on server after Phase 6.9 ghost-rig "rip the mirror rig" change.** | Auth `NetworkPlayer` was real but full-dynamic — fell off map at spawn (0, 8, 0) under gravity. No inputs driving Movement either. Nothing to push boxes server-side. | Make the auth rig kinematic + sweep-driven from client `PlayerUpdate` (essentially mirror rig v2 on a real `NetworkPlayer` with `HasControl=true`). | `a22b63c` |
| P1-2 | **Ghost rig knocks boxes off platforms during the initial move from spawn to client position.** | `UpdateGhostRigPosition` uses `Rigidbody.MovePosition` which sweeps + impulses dynamic bodies it overlaps. First move was a 30-unit jump from spawn → swept through entire box stacks. | Detect `delta.magnitude > 5f` and teleport (direct `rb.position` write, no sweep). Small subsequent deltas still use `MovePosition` so the rig can naturally push boxes when the player walks into them. | (in `a22b63c`) |
| P1-3 | **Snapshot smoothing teleports every 33ms — visible jitter.** | Client `ApplySnapshot` was `rb.position = target` (snap). At 30Hz snapshot rate the visual was teleporting every frame. | Replace with per-frame exponential lerp `rb.position = Lerp(rb.position, target, 1 - exp(-15 * dt))`. Settles 95% in 200ms; frame-rate independent. | (Phase 6.11.2) |
| P1-4 | **Boxes stop syncing after first push.** | `BroadcastWorldStateSnapshot` was skipping kinematic NSOs to save bandwidth. Landfall's animator-driven moving platforms ARE kinematic but DO move — they got dropped from the snapshot. | Switch NSO inclusion criterion from "non-kinematic" to "position changed since last broadcast" + 1s keepalive after motion stops. | `12def78` |
| P1-5 | **Damage validator falsely rejects long-range weapon hits because positions are checked too late.** | `ValidateDamagePacket` used current rig positions, but the attacker may have moved away in the ~RTT since they actually fired. | Look up positions at server tick T-2 (~66ms ago at 30Hz) for distance check — fixed-window lag-comp approximation. Falls back to current if tick history not yet available. | (Phase 6.14.5 v0.2) |
| P1-6 | **Stale-client SfClient entries leak per-slot v26 endpoints + rate guards.** | `SweepStaleClients` removed `_sfClients` entries but left `_slotV26Endpoint[slot]` and `_rateGuards[key]` pointing at the dead client. Next client reusing that slot inherited the ghost's send addr. | Clean both side-tables in the same sweep. | (Phase 6.12 hardening) |
| P1-7 | **v26 snapshot wire format breaks when projectiles are present (server allocates 22 bytes/projectile but writes 18).** | Body-length calculation included a phantom 4 extra bytes per projectile that were never written; the trailing zeros sat in the packet's steamID/channel suffix region, corrupting the envelope. | Fixed length to 18 (`u32 id + u8 slot + u8 wType + 3×f32 pos`). Also taught the client parser to skip the projectile section (don't render yet) so future additional sections stay aligned. | `5a3d252` |
| P1-8 | **Attacker-slot spoofing bypasses damage distance check.** `ValidateDamagePacket` validated the attacker-index byte for range only — it did NOT verify the body's attacker matches the sending `cli.Slot`. A malicious client could spoof `attacker=3` while being slot 1, getting the distance check from slot 3's position. | Added a slot-identity guard in `ValidateDamagePacket`: reject if `attackerIdx != 255 && sender.Slot >= 0 && attackerIdx != sender.Slot`. | `c6e9797` |
